# Production Deployment — vntr.online

Live at **https://vntr.online/app/**. Deployed to Hostinger Cloud Startup shared
hosting (CloudLinux + LiteSpeed), not a VPS — no root, no systemd, no Nginx
config access, no Python-App wizard. Everything below reflects the constraints
of that environment.

## Why it's deployed the way it is

The original plan (systemd service, Nginx, apt-installed Postgres, certbot)
assumed VPS-level access. Reconnaissance during deployment showed:

- No `sudo`, no `systemctl`, no `crontab` command for this account.
- PostgreSQL has no server binary installed (client libs only) → **switched to
  MySQL/MariaDB**, which Hostinger does provision on this plan.
- No "Setup Python App" wizard (Node.js only) → FastAPI runs manually via
  Uvicorn as a background process, not a managed app.
- `.htaccess` `RewriteRule ... [P]` (mod_proxy reverse proxying) is **blocked**
  at the platform level — confirmed by testing proxy rules against both the
  local backend and an external host, both returned a generic 503 before
  reaching either target. → **A small PHP bridge script (`api-proxy.php`)
  forwards requests to Uvicorn via `curl` instead of mod_proxy.**

## Architecture

```
Browser
  └─> https://vntr.online/app/*        (LiteSpeed, SSL via hPanel free SSL)
        ├─ /app/api/*      → api-proxy.php → curl → 127.0.0.1:8010/api/*   (FastAPI)
        ├─ /app/uploads/*  → api-proxy.php → curl → 127.0.0.1:8010/uploads/*
        ├─ real files (JS/CSS under /app/assets/*) → served directly
        └─ everything else → index.html (SPA client-side routing)
```

- **Frontend**: React/Vite SPA, built with `base: /app/` and
  `VITE_API_URL=/app` (endpoints already include their own `/api/...`
  prefix — do **not** set this to `/app/api`, it double-prefixes to
  `/app/api/api/...`, a bug hit and fixed during this deployment).
- **Backend**: FastAPI on Uvicorn, bound to `127.0.0.1:8010` only — never
  exposed directly to the internet.
- **Database**: MySQL/MariaDB 11.8, connected via `127.0.0.1` (not
  `localhost` — MySQL resolved `localhost` to the IPv6 loopback `::1`, which
  the DB user isn't granted access from; only `127.0.0.1`/Unix-socket work).

## Environment variables

`vntr_backend/.env` (never committed, not shown in chat — see the file
directly on the server):

- `DATABASE_URL` — `mysql+pymysql://...@127.0.0.1/...`
- `SECRET_KEY` — randomly generated for this deployment (JWT signing)
- `CORS_ORIGINS=https://vntr.online` (largely moot — frontend and API are
  same-origin via the `/app` proxy, so no cross-origin requests happen)
- `PUBLIC_BASE_URL=https://vntr.online/app`

  UI (provider-table pattern), not env vars


## Process management

Uvicorn runs as a plain background process (`nohup`), not a managed service:

- **Start**: `vntr_backend/start_uvicorn.sh` — idempotent, no-ops if already
  running (checks `run/uvicorn.pid`).
- **Watchdog**: `vntr_backend/watchdog_uvicorn.sh` — restarts Uvicorn if the
  pidfile is stale/missing. Verified working (killed the process manually,
  ran the watchdog, confirmed it came back up).
- **Logs**: `vntr_backend/run/uvicorn.log`, `run/watchdog.log`.

## Database migrations

Local dev's 18+ Postgres-authored Alembic migrations were **not** replayed
against MySQL (several use Postgres-only DDL, e.g. `ALTER TYPE ... ADD
VALUE`). Instead, a single fresh migration
(`alembic/versions/4804eeb47ba3_initial_mysql_schema.py`, present only in the
server copy, not local dev) was autogenerated directly against the empty
production MySQL database and applied. Local dev's own migration chain
(Postgres) is untouched.

Two Postgres-specific patterns were ported to be MySQL-portable as part of
this work — these changes **are** in the main codebase (see `git log`):
- `postgresql.ARRAY` / `postgresql.JSONB` → generic `sqlalchemy.JSON`
- `Customer.tags.any(x)` (Postgres array containment) →
  `func.json_contains(Customer.tags, func.json_quote(x))`

## Redeploying after a code change

**Backend:**
1. `cd backend && tar czf backend.tar.gz app alembic alembic.ini` (exclude
   `venv`, `__pycache__`, local `.env`, `alembic/versions/*.py` if you don't
   want to touch the production migration history)
2. Upload + extract into `vntr_backend/`
3. `./venv/bin/pip install -r requirements-prod.txt` if dependencies changed
4. `./venv/bin/alembic revision --autogenerate -m "..."` +
   `./venv/bin/alembic upgrade head` if models changed
5. Restart: `kill $(cat run/uvicorn.pid) && ./start_uvicorn.sh`

**Frontend:**
1. `cd frontend && npm run build` (production env vars come from
   `.env.production`, already committed)
2. Upload `dist/*` into `public_html/app/`, replacing the `assets/` folder
   and `index.html` — **do not overwrite** `.htaccess` or `api-proxy.php`

## Other changes made for production-readiness

- `public_html/.htaccess` (site-wide IP allowlist added during earlier SSH
  troubleshooting, which had accidentally blocked public access to the whole
  domain) — backed up and cleared, at the account owner's confirmation.
- `frontend/src/vite-env.d.ts` added — was missing, so `import.meta.env` had
  no TypeScript types and `tsc -b` (part of `npm run build`) failed. Local
  dev never caught this because `vite dev` skips type-checking.
- `backend/alembic/env.py` — escapes `%` before handing the DB URL to
  `configparser` (`configparser` treats `%` as interpolation syntax, which
  broke when the MySQL password's URL-encoded `@` → `%40` was substituted in).
